# Triage

Read the [tracker](../../../docs/agents/issue-tracker.md) and
[label mapping](../../../docs/agents/triage-labels.md). Inspect incoming issues
or a named PR, verify claims, and produce a durable recommendation or brief.
Read-only triage requests stay read-only; apply an outcome when the user asks.

## Classify

Use bug/enhancement as prose categories and needs-triage, needs-info,
ready-for-agent, ready-for-human, or wontfix as reasoning states, not GitHub
labels. Existing priority, effort, holds, and workflow labels remain authoritative.
`ready-for-agent` means sufficiently specified, not authorized to start.

## Discover

For a queue request, show oldest items lacking a clear disposition, waiting for
information with new reporter activity, or needing maintainer decisions. Inspect
bodies and comments rather than querying nonexistent upstream role labels.
Include external PRs only if explicitly requested or enabled in the tracker doc.
Resolve a named issue/PR against GitHub before choosing its workflow.

## Triage an item

1. Read its body, comments, labels, author, and linked docs; for a PR read the
   diff. Search by domain concept for existing implementation, duplicate issues,
   and previous rejections in open and closed GitHub discussions.
2. Report the current behavior and proposed disposition with code evidence.
   Reuse prior answers. If verification requires running tests, follow the
   project PR-before-local-tests rule and the relevant development/smoke skill.
   Call an unrun reproduction unverified; do not invent confirmation.
3. Resolve missing facts yourself. For unresolved product decisions, use the
   relevant questions from `grilling` and `domain-modeling` when needed.
4. For an authorized update, use [AGENT-BRIEF.md](AGENT-BRIEF.md) to capture
   current/desired behavior, acceptance criteria, and remaining uncertainty.
   Link canonical planning documents; a brief never replaces an approved spec.
5. Follow the exact existing label policy, preserving unrelated labels and
   `backlog`. Close or reject only when the user authorized that outcome. Record
   a durable rejection using [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) when appropriate.
6. Read every mutation back. Stop on an uncertain outcome instead of retrying
   blindly. Report what changed and what remains unverified.

Start generated triage comments with `> *This was generated by AI during triage.*`.
For needs-info notes, separate established facts from specific missing answers.
On resumption, inspect new replies and update the assessment without repeating
settled questions. A state override changes disposition, not implementation scope.
